# Phase C plan: heavy work becomes server jobs (written 2026-11-15, before any code)

Read with `docs/TARGET-ARCHITECTURE.md` (section 6, phase C) and `docs/PHASE0-FINDINGS.md` (the inventory). Rule for every step: the live site on the owner's PC keeps working exactly as it does today; each step is built beside the current path, **behind a switch that is OFF by default**, and the old path stays until the new one has worked for a week.

## Why start with the library
The library browser fetches a Mafteiach page and parses it (up to 3 MB of HTML) on the website on every browse, relying on a one-hour Next.js fetch cache that does not exist on Cloudflare. Daily study fetches and parses a day's page on first request. Both are too heavy for the 10 ms limit and rude to the sources once several schools use them. Their output already goes into Supabase tables (`library_daily_texts`, `library_sie_entries`) or is returned as JSON, and no school file is involved: the safest first move.

## The mechanism (C1)
1. **`library_pages`** (shared read-through cache): `key` (primary key, built from a fixed shape, e.g. `likkutei:12`, `list:maamorim:5710`, `entry:/maamorim/123`, `daily:2026-11-15:tanya`), `kind`, `payload` (parsed JSON, size-capped), `source_url`, `fetched_at`, `expires_at`, `fetched_by` (agent id). Everyone signed in may read it (public library data, like `library_daily_texts`); only the service role writes it.
2. **`server_jobs`**: `id`, `kind` (`library_fetch` first), `organization_id` (who asked), `requested_by`, `params` (a small structured object, never a URL), `dedupe_key` (one active job per key), `status` (queued / claimed / done / failed / expired), `claimed_by`, `lease_until`, `result_key`, `error`, timestamps. Members read their own school's jobs (to show progress); only the service role writes.
3. **Website** (a server action, unchanged signature for the screens): read `library_pages`; if fresh, return it. If missing or stale: with the switch OFF, do today's live fetch; with the switch ON, enqueue a job (deduped) and return "pending"; if no server that can fetch is online (heartbeat older than about 2 minutes), return "print server offline, try again when it is on".
4. **Agent** (only a server flagged as a library fetcher, the owner's, and only when `PRINTIO_LIBRARY_WORKER` is set): a separate small loop, never in the print loop. It claims a job, rebuilds the URL itself from `params` with the shared URL builder, fetches politely (at least 5 s between requests, 15 s timeout, 3 MB cap), parses with the shared parsers, and posts the parsed result to a website endpoint that validates it and writes `library_pages`. Interim: these two endpoints (`claim`, `complete`) live on the website; in phase D they become database functions.
5. **Parsers move** from `apps/web/lib/library/*` into `packages/shared` (pure TypeScript, with their tests and fixtures) so the agent and the website use the same code. This is a pure refactor and is the first PR (C1a).
6. **Week-ahead daily text** (C1d): the owner's server enqueues and fetches the next 7 days at a quiet hour; old days are pruned after about 60 days.

## Sub-steps (one PR each, one agent at a time)
- **C1a** move parsers and URL builders to `packages/shared`, no behaviour change. Gate: all tests green, the page works as before.
- **C1b** migration (tables, explicit grants, RLS), website read-through logic behind the switch, the two agent endpoints, the isolation-test matrix updated for the new tables (the test fails closed until their access is stated), tests.
- **C1c** the agent library worker, isolated, off by default, with tests.
- **C1d** waiting states in the UI, then the week-ahead schedule.
- **Switch on** only after the owner has pressed Update now on the PC and watched a fetch complete; roll back by switching off.

## How this could fail (and what stops it)
| Risk | Prevention |
|---|---|
| Breaking the library the owner uses today | Switch OFF by default; old live-fetch path kept; flip only after a real fetch worked |
| The agent update disturbs printing (the agent prints) | The worker is a separate async loop, wrapped in try/catch, concurrency 1, hard timeouts, only runs when its env flag is set; it cannot block the print loop; unit-tested for "fetch hangs", "parse throws", "server returns garbage" |
| A school server poisons the shared cache | Only agents flagged as library fetchers may complete jobs; schema validation (zod), key must match the allowed shapes, size cap, first writer wins until expiry, `fetched_by` recorded, owner can purge a key |
| SSRF (fetching an address the cloud chose) | Job params are structured; the agent builds the URL from the fixed allow-list (`libraryPageUrl`); a URL is never accepted from the cloud; redirects must stay on the source's origin |
| Job spam or stampede (20 people open the same page) | `check_rate_limit` per user; one active job per `dedupe_key`; global cap on queued jobs; queued jobs expire after 10 minutes |
| A job stuck because the agent died mid-claim | `lease_until`; the next claim reclaims an expired lease; the UI says "taking longer than usual" after a timeout instead of spinning |
| The source changes its page (parser sees nothing) | Job fails with reason `different`; negative result cached for 5 minutes only; the screen says so plainly (as it does today) |
| Browser polling eats Cloudflare requests later | Realtime subscription on the job row and the cache row, with a slow backstop poll (5 s, capped at 60 s total); never a tight loop |
| Database growth | Payloads capped; delete pages not read for 30 days; daily text pruned after about 60 days |
| Too much power on the website endpoints | They are agent-authenticated, owner-agent only, rate limited, validate everything, and write only the two cache tables |
| Migrations that cannot be rolled back | Additive only; new tables with explicit grants (never `anon`); mirrored in `schema.sql`; reversible by dropping the new tables |
| The owner's PC not updated | Switch stays off until Update now was pressed and a test fetch worked |

## Status
C1a done (2026-11-15): parsers, URL builder, SIE data and helpers, daily parsers and dates moved to `packages/shared/src/library/` with their tests and fixtures; imported as `@printio/shared/library/...` (subpath exports; `node-html-parser` added to shared).

**C1b done (website side only, 2026-11-15; no agent code yet).** The library browser can now read a shared cache that a print server fills through jobs, behind a switch that is OFF by default. With the switch off the website behaves exactly as before (live fetch; the old code path is untouched and its tests pass unchanged).
- **The switch**: environment variable `LIBRARY_VIA_SERVER` on the website (`1` or `true` = on; unset or anything else = OFF). One helper, `libraryViaServer()` in `apps/web/lib/library/cache.ts`; documented in `apps/web/.env.example`. Changing it needs a website restart.
- **Migration `0055_library_cache_and_jobs.sql`** (additive, re-runnable, NOT yet applied to the live database): `library_pages` (shared cache, every signed-in member reads, service role writes), `server_jobs` (the queue; the requesting school's members read, service role writes; one active job per `dedupe_key` via a unique partial index), `library_fetchers` (the print servers allowed to fill the cache; no access at all for signed-in users; a separate table, not a flag on `agents`, because school admins can update their own `agents` rows). Explicit grants, nothing for anon; mirrored in `supabase/schema.sql` and `database.types.ts`. The two-school isolation matrix states the access for all three and fails if it drifts.
- **Switch ON behaviour** (`app/(dashboard)/print/library/actions.ts`): fresh `library_pages` row -> same result shape as today; otherwise, if no registered print server has reported in within 2 minutes -> `{ ok:false, offline:true }`; otherwise a per-person rate limit, then one shared job per page -> `{ ok:false, pending:true, jobId }`. A job that failed in the last 5 minutes shows its error instead of queueing again; at most 50 jobs wait in the queue. Cache lifetime: lists and Likkutei volumes 24 hours, single entries 7 days. The browser shows the message with a "Try again" button (no polling, no Realtime yet; that is C1d).
- **Endpoints** (agent bearer auth, caller must be in `library_fetchers`): `POST /api/agents/server-jobs/claim`, `POST /api/agents/server-jobs/:jobId/complete`, `POST /api/agents/server-jobs/:jobId/fail`. See `docs/agent-api.md`. `complete` rebuilds the cache key and source address from the job's own params, validates the payload with zod against the page kind the job asked for (limits on string and list sizes, only https Google Drive/Docs links, total 1.3 MB), and refuses a body that carries a key or an address. No endpoint accepts or returns a URL.
- **To turn it on later** (only after C1c is deployed and a test fetch worked): 1) apply `0055` to the live database; 2) register the owner's print server in the Supabase SQL editor: `insert into library_fetchers (agent_id) values ('<agent uuid>');` (the agent's id is on its page under Admin > Agents); 3) set `LIBRARY_VIA_SERVER=1` for the website and restart it. Roll back: unset it and restart; to stop a server filling the cache: `delete from library_fetchers where agent_id = '<agent uuid>';`.
- **Not done yet**: waiting states with Realtime/slow polling and the week-ahead daily text (C1d). (Queued jobs now expire after 10 minutes: see C1c below. A claimed job whose lease ran out is retaken.)

**C1c done (agent side, 2026-11-15).** The print server can now fill the shared cache. It is a separate worker inside the agent, OFF by default.
- **The switch**: environment variable `PRINTIO_LIBRARY_WORKER` in the agent's `apps\agent\.env` (`1` or `true` = on; unset or anything else = off, never an error). Off: nothing is created (no timer, no network call, one debug log line). Read in `apps/agent/src/config.ts` (`libraryWorker`), started from `apps/agent/src/index.ts` only when on, stopped in the same `shutdown` as the other loops. Only for the owner's own server; it also needs the server in `library_fetchers`.
- **Code**: `apps/agent/src/library-worker.ts` (tests in `apps/agent/test/library-worker.test.ts`, plus the three new calls in `cloud-client.ts`: `claimLibraryJob`, `completeLibraryJob`, `failLibraryJob`). Uses the agent's existing cloud client (same login, address and error types). The three calls deliberately do not feed `consecutiveAuthFailures` (that number slows the print loop), so a 403 from this worker can never slow printing.
- **Behaviour**: own timer (first look 5 s after start, then about every 20 s when idle, 1 s between jobs), one job at a time. A job that is not `library_fetch` is failed ("unsupported job type"). Otherwise the address is rebuilt from `params` with `libraryPageUrl` (never a cloud-sent address; none possible -> fail "address not allowed", nothing fetched), fetched with `user-agent: Printio/1.0 (print library browser)`, 15 s limit (headers and body), 3 MB cap read from the stream (stops and drops the rest), redirects followed by hand and only onto the library's own origin (up to 3), at least 5 s between the end of one library request and the start of the next (across jobs). Parsed with the shared parsers; an empty volume or list is "page looks different" (same rule as the website; a single entry has no emptiness rule, as on the website). `complete` gets exactly `{ payload }`; `fail` gets `{ error }` with one of: `could not reach the library`, `page not found`, `page too large`, `page looks different`, `address not allowed`, `unsupported job type`, `the library answered with an error (NNN)`.
- **Safety**: errors talking to the website back off 20 s, 40 s ... capped at 5 minutes; a 403 on claim logs ONE clear line and then only asks about every 10 minutes; a 400/413 from `complete` is logged once and the job is failed once (never retried in a loop); other 4xx are logged once and dropped; a job not finished within the 120 s lease is abandoned (the website hands it out again). Every entry point catches and logs; the timer is `unref`'d; `stop()` aborts a running fetch and posts nothing.
- **Website follow-up** (`claim` route): before claiming, `queued` jobs older than 10 minutes are marked `failed` with error `expired` (then the website's "failed in the last 5 minutes" rule applies).
- **How to run it on the owner's PC**: see `docs/agent-install.md`, "The library worker" (exact steps in order: pull and `setup-web.ps1`, apply `0055`, register the server in `library_fetchers`, `PRINTIO_LIBRARY_WORKER=1` + restart the agent, queue one test job by hand, then `LIBRARY_VIA_SERVER=1` on the website). `setup-web.ps1` now keeps `LIBRARY_VIA_SERVER` when it rewrites `.env.production.local`.
- **Still to do**: C1d (waiting states in the UI, then the week-ahead daily text).
