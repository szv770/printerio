# Printio web review (read-only)

Commit reviewed: d954584 (branch claude/fix-flaky-imposition-test). Nothing was edited, no DB/Vercel touched. Typecheck/lint/tests were NOT run (code reading only).
Paths are relative to the repo root. "UNVERIFIED" = could not be confirmed from code alone.

Headline: the app code is carefully written, but the database permissions underneath it are much looser than the app assumes. The browser holds the public Supabase key plus the member's own login, so anything an RLS policy allows is reachable without going through the Next.js actions. Findings 1-3 are the ones to fix first. Findings 4-5 are the ones that will visibly hurt teachers in week one.

---

## Ranked findings

### 1. CRITICAL - Any member can self-approve, skip policy/quota, and edit their own jobs directly in the database
- File: supabase/migrations/0006_rls_policies.sql:302-325 (policies "members can create jobs..." and "owners can update own jobs..."), supabase/migrations/0031_explicit_table_grants.sql (full column grants to `authenticated`).
- What: `print_jobs` INSERT only checks `created_by = auth.uid()` and org membership. UPDATE lets the owner change ANY column of their own row (`using/with check created_by = uid`). The transition trigger only validates status edges, and `pending_approval -> approved` is a legal edge.
- Scenario: a teacher opens the browser console on the live site (anon key and their session are right there) and runs `supabase.from('print_jobs').update({status:'approved'}).eq('id', myPendingJob)`. The approval rule is bypassed. They can also INSERT a row with `status:'approved'`, `copies:500`, `estimated_physical_sheets:0`, pointing at any printer profile, skipping policy, quota and approval entirely. Because UPDATE is unrestricted they can also change `organization_id`, `printer_profile_id`, `copies` after approval, or `derived_file_path`.
- Fix (smallest): remove the member INSERT policy and the owner UPDATE policy on `print_jobs` (all job writes already run server-side; the web actions would need to use the service-role client for the insert and for the few owner updates, like cancel). Alternative if you want to keep member-client writes: `revoke insert, update on print_jobs from authenticated` plus a column-level `grant update (status)` limited by a BEFORE UPDATE trigger that only allows `-> cancelled` for non-approvers.

### 2. CRITICAL - Any member can zero out or rewrite their own quota usage
- File: supabase/migrations/0006_rls_policies.sql:398-408; supabase/migrations/0010_quota_functions.sql (function is SECURITY INVOKER, relies on those policies).
- What: `monthly_usage` INSERT/UPDATE policies allow `user_id = auth.uid()` with full column grants. `adjust_monthly_usage` is callable by any authenticated user with arbitrary amounts and mode.
- Scenario: `update monthly_usage set physical_sheets_used = 0, reserved_physical_sheets = 0` from the console resets the monthly cap. Calling the RPC with `consume` and negative amounts has the same effect. The quota is advisory, not enforced.
- Fix: drop the member INSERT/UPDATE policies on `monthly_usage`; make `adjust_monthly_usage` SECURITY DEFINER with `revoke execute ... from authenticated` and call it only with the service-role client (the code already does this in 4 of 6 places; `create-print-job.ts:643` and `:675` use the member client and need switching).

### 3. HIGH - Any member of the org can list, download and overwrite every colleague's uploaded documents
- File: supabase/migrations/0007_storage.sql:13-45.
- What: storage SELECT/INSERT/UPDATE policies on bucket `print-jobs` only check the org segment of the path (`org/<orgId>/...`), not who owns the job. SELECT permits `list`, so job ids can be enumerated.
- Scenario: any teacher runs `supabase.storage.from('print-jobs').list('org/<orgId>/jobs')` then downloads other teachers' PDFs (IEPs, grades, HR letters). Worse, the UPDATE policy lets them overwrite `derived.pdf` of someone else's queued job, so the printer prints attacker-chosen content under another person's name.
- Fix: restrict member policies to jobs they own (`exists (select 1 from print_jobs j where j.id = <jobId from path> and j.created_by = auth.uid())`), keep approver/admin read via `private.is_org_approver`, and drop member INSERT/UPDATE entirely by moving uploads to the service-role client (server already has the bytes in `create-print-job.ts:696-701`).

### 4. HIGH - A job that fails once is stuck forever and its quota stays reserved
- File: app/api/agents/jobs/[jobId]/claim/route.ts:63 (only claims `status = 'approved'`), app/api/agents/jobs/claimable/route.ts (lists only `approved`), app/api/agents/jobs/[jobId]/status/route.ts:90, app/api/cron/sweep/route.ts step 3, lib/retention.ts:241.
- What: the state machine documents `failed -> claimed` as the retry edge and the UI says "Attempt 1 of 3", but nothing ever moves a failed job back to `approved` or `claimed`. I searched web and agent code: no retry path exists. The quota reservation is only released when `attempt_count + 1 >= max_attempts`, which can never be reached because attempt 2 never happens. Retention also refuses to purge a failed job's file while attempts remain (`retention.ts:241`).
- Scenario: the printer jams, the agent reports `failed`. The teacher sees "failed", presses Print again (new job, new reservation), and the first job's reservation sits in `reserved_*` for the rest of the month. A teacher with a 100-sheet quota who hits 3 transient failures can lose most of their month. Their PDFs also never get purged.
- Fix: in the status route (and the sweep), when `failed` and `attempt_count + 1 < max_attempts`, set status back to `approved` (clearing the lease) so the normal claim loop retries it; only release quota when exhausted. Also add a manual "Retry" for admins.

### 5. HIGH - Uploads from the website over about 4.5 MB will fail on Vercel
- File: apps/web/next.config.ts:30 (`bodySizeLimit: "100mb"`), app/(dashboard)/print/actions.ts:43 (file goes through a Server Action), lib/pdf/client-precheck.ts:19 (default limit 50 MB).
- What: the PDF is posted as part of a Server Action request. Vercel Functions reject request bodies over about 4.5 MB (platform limit, `FUNCTION_PAYLOAD_TOO_LARGE`), regardless of Next's own setting. UNVERIFIED against the live deployment, but this is a documented Vercel limit.
- Scenario: a teacher uploads a scanned worksheet (8 MB). The page says 50 MB is allowed, the browser shows a generic failure after a long upload, no job is created.
- Fix: upload straight to Supabase Storage from the browser using a signed upload URL (the IPP path already does this via `gateway-intake/`), then call the action with the storage path. Short term, lower `max_upload_size_bytes` default to 4 MB and say so on the form.

### 6. HIGH - Held jobs from the print dialog are a dead end (except booklet)
- File: app/(dashboard)/jobs/[id]/JobStatusLive.tsx:233-239.
- What: when an IPP job is held for any reason other than the booklet binding question (colour, A4, unsupported finishing, bad page range), the only action is "Choose your options again", a link to a blank Print page. The document the teacher sent from their phone is not carried over; they would have to find a PDF they never had.
- Scenario: Android teacher prints a Google Doc with colour requested; job is held "waiting for you to choose how to print it on the website". They open the site, see an empty upload form, give up, job expires silently after 7 days.
- Fix: add a "Choose options" card for any held job (same pattern as `HeldBookletCard`) that calls a generalised `finishHeldJobAction` using the stored original. Also email/notify nothing today: consider showing held jobs on the home page.

### 7. HIGH - No way for a member to cancel their own job from the website
- File: app/(dashboard)/jobs/[id]/actions.ts (only `deleteJobFileAction`), no cancel action anywhere under app/(dashboard).
- What: only the IPP gateway can cancel (`api/gateway/jobs/[jobId]/cancel`). A web user cannot cancel a pending-approval or approved job; only an admin can reject a pending one, and nobody can cancel an `approved` one before the agent claims it.
- Scenario: teacher sends 300 copies by mistake. The job is auto-approved and prints; there is no stop button.
- Fix: add `cancelJobAction` mirroring the gateway cancel route (guarded `.eq('status', current)`, release quota for `pending_approval/approved`, event row) and a Cancel button on the job page and list.

### 8. HIGH - The sweep (lease expiry, stuck jobs) only runs once a day
- File: .github/workflows/cron-sweep.yml:15-22 (15-minute schedule commented out, "project on hold"), apps/web/vercel.json:5 (`0 8 * * *`).
- What: `claim` and `claimable` only look at `status = 'approved'`, so a job whose agent crashed after claiming stays `claimed` (or `downloading/printing`) until the daily sweep; held/pending expiry is also day-granular. Docs and code comments still describe a 15-minute cadence.
- Scenario: agent restarts mid-claim at 9 am; the teacher's job does not print until 8 am next day.
- Fix: re-enable the schedule in cron-sweep.yml (one uncomment) or make `claimable`/`claim` also accept `claimed` with an expired lease so recovery does not depend on the sweep.

### 9. HIGH - Last admin can be demoted (organization locked out)
- File: app/admin/users/actions.ts:51-75 (`changeMemberRoleAction`), :140-165 (`toggleMemberStatusAction` only blocks disabling yourself).
- What: removal has `assertCanRemoveMember`, but role change has no guard. A sole org_admin can set their own role to "User" or an admin can demote the other admin concurrently.
- Scenario: the owner (non-technical) changes their own role dropdown by accident; nobody can reach Admin; recovery needs SQL or the platform console.
- Fix: before updating, if target is an active org_admin and the new role is not org_admin, count remaining active org_admins and refuse if it would reach zero (reuse `assertCanRemoveMember`'s logic).

### 10. MEDIUM - Printer shows "Offline" forever for direct-port printers, and "Ready" forever for dead agents
- File: app/api/agents/heartbeat/route.ts:136-146, app/(dashboard)/print/page.tsx:48.
- What: the heartbeat only updates `printers.status` by matching `windows_queue_name`. A raw (direct port 9100) profile has no queue name (see download-url route comment "Raw profiles carry no Windows queue"), so its printer likely stays `unknown` and the member form labels it Offline. Conversely, nothing ever ages `status` out when heartbeats stop, so a dead agent still shows "Ready". UNVERIFIED for the raw case (depends on how setup stores the profile).
- Fix: derive "Ready" from the agent's `last_seen_at` (a helper `isAgentOnline` already exists in lib/agent-detail.ts) instead of `printers.status`; also use it in the gateway `finalize` (`agents.status = 'active'` does not mean alive) to return `no_printer` honestly.

### 11. MEDIUM - Agent status report is not idempotent: double consume of quota on a retried request
- File: app/api/agents/jobs/[jobId]/status/route.ts:41-91.
- What: it reads the job, checks `canTransition`, then updates with no `.eq('status', job.status)` guard; the consume RPC runs afterwards and its errors are not handled. Two overlapping `completed` reports (agent retry after a timeout) both pass the check and both consume, double-counting usage. If consume throws after the status update, the response is 500, the agent retries, gets 409 `illegal_transition`, and the reservation leaks.
- Fix: make the update conditional on the old status and only adjust quota when the update returned a row; wrap the RPC in try/catch with logging.

### 12. MEDIUM - Quota month is UTC and a job can reserve in one month and settle in another
- File: lib/quota.ts:23 (`currentPeriod` uses UTC), consumed at status route / sweep / approvals with `currentPeriod()` at release time.
- What: a job reserved on Oct 31 (or approved after a 72 h approval wait) is consumed/released in the new month's row. The release clamps at 0 in a row that holds nothing, so the old month keeps a ghost reservation; consume adds usage to the new month. Also, a US school's evening of the 31st already counts as November.
- Fix: store the period on the job (or on the reservation) at reserve time and pass it to release/consume; add an org time zone setting (see #13).

### 13. MEDIUM - No time zone setting: UTC dates on stamps, audit log and quota
- File: lib/jobs/user-code.ts:66 (stamp date `toISOString().slice(0,10)`), app/admin/audit/page.tsx:32 (server-side `toLocaleString()`), lib/quota.ts:23.
- What: the stamp printed on page 1 shows the UTC date (an 8 pm EDT job is stamped tomorrow). The audit page formats times on the server, so admins see UTC. Member job pages correctly use `LocalTime`.
- Fix: add `timezone` to organization_settings, use it for the stamp and quota period; render audit times via `LocalTime`.

### 14. MEDIUM - A rejected/expired race double-releases someone else's reserved quota
- File: app/admin/approvals/actions.ts:90-100,104-170 (update not guarded by status), app/api/cron/sweep/route.ts step 1.
- What: approve/reject update `print_jobs` by id only; `loadPendingJob` checks the status earlier. If the sweep expires the job between the check and the update (or two approvers click), release can run twice. Release works on the user's shared monthly row (clamped at 0), so a second release eats the reservation of the same user's other pending jobs.
- Fix: add `.eq('status','pending_approval')` and `.select('id')`, and only release when a row was updated.

### 15. MEDIUM - Double-submit on "Finish this booklet" creates two jobs
- File: app/(dashboard)/print/actions.ts:163-222.
- What: the new job is created first and the held one is closed afterwards with a guard. Two quick taps (or retry on a bad connection) both pass the `held` check and each create a new job and reserve quota; only one closes the held job.
- Fix: claim the held job first (`update status='cancelled' ... where status='held'` returning a row) and only then create the new one, restoring on failure; or add a unique `replaces_job_id`.

### 16. MEDIUM - Gateway finalize is not idempotent
- File: app/api/gateway/jobs/finalize/route.ts:74-118.
- What: the intake object is deleted only after success, so if the web response is lost (60 s function timeout, network) and the gateway retries, a second job is created from the same file: double print and double quota.
- Fix: derive the job id from the intake path (deterministic uuid) or store `intake_path` unique on `print_jobs`, and return the existing job on retry.

### 17. MEDIUM - Reports silently truncate at 1000 rows
- File: app/admin/reports/page.tsx:44-52 (90 days of `print_jobs`, no `.range()`/limit), also app/admin/users/page.tsx:12 (roster) and approvals page.
- What: PostgREST's default row cap is 1000; a busy school exceeds it in 90 days. Totals, "top users", colour share and CSV export are then wrong with no warning.
- Fix: aggregate in SQL (a view or RPC `group by`), or page through with `.range()` until exhausted.

### 18. MEDIUM - My jobs shows only the latest 50 with no way to see older
- File: app/(dashboard)/jobs/page.tsx:24.
- Fix: add a "Show older" link (cursor on `created_at`) or a month filter.

### 19. MEDIUM - Invitation codes default to unlimited uses and never expiring
- File: app/admin/users/InviteForm.tsx:25-30, app/admin/users/actions.ts:26-33.
- What: leaving the two fields blank creates a permanent multi-use code. With role selectable up to Admin, a leaked code in a staff email is a standing way in (for anyone who passes the domain gate).
- Fix: default Max uses to 1 and Expires to 7 days; warn on admin-role codes.

### 20. MEDIUM - Sign-in link is sent to anyone; the domain check only runs after they click
- File: app/login/MagicLinkForm.tsx:44 (`signInWithOtp` creates users by default), app/auth/callback/route.ts:80-100.
- What: a teacher who types a personal address gets an email, clicks, and then lands on "no access". Strangers can also create junk auth users and use the form to email arbitrary addresses (Supabase rate limits apply). The domain RPC fails open on any error (`callback/route.ts:84-96`).
- Fix: server-side action that checks the domain list (or existing membership) before sending; pass `shouldCreateUser:false` once members are invited/known; show the allowed domain on the login page.

### 21. MEDIUM - Member-forged audit events
- File: supabase/migrations/0006_rls_policies.sql:341-352.
- What: members can insert `print_job_events` on their own jobs with `actor_type 'user'` and any `event_type` (e.g. `APPROVED`, `JOB_COMPLETED`). The job page "History" and the stepper (built from events) can then lie. Related: members can also insert `member_devices` rows with a chosen `token_hash` and unlimited count (0032).
- Fix: remove the member insert policy; write events server-side only.

### 22. MEDIUM - Held and "approved" jobs still print if the printer/agent is gone; no feedback
- File: app/api/gateway/jobs/finalize/route.ts:57-69, create-print-job.ts (no check that the profile's agent is alive).
- What: a job is accepted for a printer whose agent has been offline for days; the teacher gets "queued" and nothing prints until the agent returns (and then maybe days later).
- Fix: warn at submit time when the agent's `last_seen_at` is older than a few minutes (see #10); optionally refuse.

### 23. LOW/MEDIUM - Agent authentication costs a scrypt on every request
- File: lib/agent-auth.ts:45-68.
- What: every poll (claimable, heartbeat, commands, status) runs `scryptSync` (blocking, ~50-100 ms CPU) after a DB read. Many polls from a few agents is fine, but anyone who knows an agent id (a UUID shown in admin URLs) can burn CPU with bad secrets; there is no rate limit on these routes.
- Fix: cache a verified (agentId, sha256(secret)) pair for a minute in memory, or use a fast hash for a 256-bit random secret (scrypt is unnecessary for high-entropy secrets).

### 24. LOW/MEDIUM - Admin pages use `confirm()` dialogs; inconsistent with the rest of the app
- File: app/admin/users/MembersTable.tsx:166, app/admin/printers/PrintersPanel.tsx:389, app/admin/agents/AgentsPanel.tsx:192, app/admin/users/InvitationsList.tsx:53, MemberDetailControls.tsx:114.
- What: native browser dialogs on destructive actions, while `DevicesView` has an accessible inline confirm with Escape handling. On phones they are easy to dismiss wrongly; they cannot be styled or described to screen readers consistently.
- Fix: reuse the DevicesView inline-confirm component.

### 25. LOW/MEDIUM - Users table: five separate save forms per row, no search, 6 columns on a phone

- What: role, department, code and status each have their own Save button; the table scrolls horizontally on a 375 px screen; no search or sort for a school with 100+ staff. Role/department inputs in the row have no accessible labels (only the code field has `aria-label`).
- Fix: move editing to the member detail page (already exists), keep the table read-only with search, add `aria-label`s.

### 26. LOW - Audit log is raw

### 28. LOW - "User" vs "Staff" roles are indistinguishable to the owner

- What: the stored `student` role is correctly shown as "User" everywhere I found, but there is also a "Staff" role with (as far as I saw) no different behaviour; the invite form lists both. Not verified whether policy rules treat them differently.

### 29. LOW - Callback failure is silent

- What: if the OAuth `code` exchange fails, the user is redirected to `/` and bounced to login with no message (only the token-hash path shows `link_invalid`).

### 30. LOW - Redeeming an invitation code has no rate limit, and a failed insert burns a use
- File: app/no-access/actions.ts, lib/auth/invitations.ts:49-63.
- What: `claim_invitation_use` increments before the member insert; if the insert fails (race with `already_member`) the use is consumed. Codes are 48-bit so brute force is impractical, but no throttling exists.

### 31. LOW - Heartbeat does one UPDATE per queue, serially

### 32. LOW - Uploads to storage are unbounded for members

## Checked and found OK (no action)
- Service-role client is `server-only`; no client component imports it; no secrets reach the browser. Logger redacts secret-looking keys. Auth callback has no open redirect (fixed paths only); only `email`/`magiclink` OTP types accepted.
- `/api/gateway/*` routes: constant-time shared-secret check, zod bodies, device/membership re-checked per request, intake path pinned to the device folder, cancel guarded on status. Good.
- `/api/agents/*`: every job route re-checks organization and lease owner; claim is an atomic conditional UPDATE; cron routes use constant-time secret compare.
- Server actions I read (print, reprint, jobs file delete, devices, approvals, users) all re-derive identity server-side and scope by org/user. IDOR via ids in forms: none found beyond the direct-DB issues above.
- `member_devices.token_hash` is correctly hidden with column-level grants.
